# 运营智脑 OpsCompass · OS 内核设计（v0.11.0）

> 版本：v1.0（草案） | 日期：2026-10-08 | 归属：开源范围 | 关联：docs/OPEN_SOURCE_PLAN.md 第九章

## 1. 设计目标与原则

### 1.1 目标

v0.10.1 已具备 13 功能页 / 15 接口模块 / 54 表 / 48 权限点的完整基础能力。本版**不新增业务页面**，只补内核能力，使产品从「单体应用」变为「可插拔平台」。

| 编号 | 目标 | 验收口径 |
|---|---|---|
| K1 | 业务模块解耦 | 任意两个非内核模块之间零直接调用，跨模块协作一律经事件总线 |
| K2 | 插件可独立交付 | 一个插件可独立开发、独立安装、独立升级、独立卸载，不改内核代码 |
| K3 | 长任务可编排 | 跨模块多步任务可编排、可重试、可中断、可追溯 |
| K4 | 时限可约束 | 任意任务/工单可挂 SLA，临期与逾期可自动催办升级 |
| K5 | 身份可治理 | 插件权限纳入既有 RBAC 体系，权限点可注册、可审计 |
| K6 | 模型可路由 | 业务代码不关心模型在哪，按策略路由本地/云端，可降级 |

### 1.2 设计原则

1. **向后兼容优先**：v0.11.0 不得破坏 v0.10.1 既有 138 接口 / 54 表 / 48 权限点；老模块可继续直连内核，新模块必须走插件接口。
2. **渐进式改造**：内核能力一次设计、分批启用，不要求既有五域一次性重构。
3. **单机可跑**：内核不引入新的必需容器，不依赖消息中间件，复用 PostgreSQL + Redis 实现。
4. **默认安全**：插件默认无任何数据权限，权限需显式声明并经管理员授予。
5. **可观测优先**：所有内核动作产生 trace_id 与审计记录。

## 3. 内核能力设计

### 3.1 事件总线（Event Bus）

**定位**：模块间唯一允许的异步协作通道。

| 项 | 设计 |
|---|---|
| 传输 | PostgreSQL 表 `os_core_event` 做持久化队列 + Redis 做唤醒通知（无中间件依赖） |
| 投递语义 | 至少一次；消费幂等由订阅方按 `event_id` 去重 |
| 事件结构 | `event_id / event_name / payload(JSON) / trace_id / tenant_id / occurred_at / version` |
| 订阅 | 订阅方注册 `(event_name, handler, 并发度, 重试策略, 死信策略)` |
| 重试 | 指数退避，默认 5 次，超限入死信表 `os_core_event_dead` |
| 顺序 | 分区键（tenant_id + 聚合ID）内保序 |
| 回放 | 支持按时间窗重放，用于故障恢复与新增订阅方补数 |
| 命名规范 | `域.对象.动作`，如 `sentiment.emotion.labeled`；内核事件前缀 `core.` |

**并发与容量**：单实例默认 8 个消费协程；事件表按 7 天热数据 + 归档策略，支撑日均百万级事件。

### 3.2 工作流引擎（Workflow Engine）

**定位**：把跨模块的多步动作编排成可追溯、可恢复的流程。

| 项 | 设计 |
|---|---|
| 流程定义 | YAML/JSON DSL，支持 `task`（执行单元）/ `branch`（条件）/ `parallel`（并行）/ `wait`（等待事件或人工确认）/ `retry` |
| 执行模型 | 状态机驱动，每步落库 `os_core_workflow_instance` + `os_core_workflow_step`，中断后可续跑 |
| 触发 | 手动、定时、事件触发（订阅内核事件总线） |
| 人工节点 | `wait` 类型步骤生成待办，等人认领/审批，可设超时兜底分支 |
| 补偿 | 失败支持回滚步骤链（定义 `compensate` 动作），无补偿则标记人工介入 |
| 幂等 | 步骤以 `instance_id + step_seq` 为幂等键 |
| 与 SLA | 每步可挂 SLA，交由 3.4 计时催办 |

**内置流程模板（本版）**：`数据采集→打标→统计` 三段式、`预警生成→通知→认领→升级`、`报告生成→人工确认→导出`。

### 3.3 插件运行时（Plugin Runtime）

**定位**：让业务能力成为可独立装卸的插件。

| 项 | 设计 |
|---|---|
| 插件形态 | 目录包：`plugin.yaml`（清单）+ `backend/`（服务端）+ `frontend/`（前端产物）+ `migrations/`（建表脚本） |
| 发现方式 | 扫描 `plugins/` 目录（内置） + 上传安装包（商业插件，签名校验） |
| 加载 | 进程内加载（Python 包导入），内核只认接口不认实现 |
| 生命周期 | `installed → enabled → disabled → uninstalled`，禁用即停路由与订阅，数据保留 |
| 隔离 | 独立表命名空间（`os_<plugin>_*`）、独立权限点、独立事件命名空间、独立配置分区 |
| 版本 | 语义化版本，声明 `min_kernel_version`；不满足则拒绝启用 |
| 升级 | 支持迁移脚本顺序执行；失败回滚到上一版本快照 |
| 前端 | 插件提供前端产物与路由声明，内核动态注册菜单与路由 |

**约束（硬性）**
1. 插件**不得**直接 import 其它插件的模块，只能发事件或调内核 API；
2. 插件**不得**直接建表，须经迁移脚本由内核统一执行；
3. 插件**不得**自行实现鉴权，必须调用内核权限校验；
4. 官方商业插件与社区插件使用**同一套接口**，不得私有 fork 内核。

### 3.4 任务 SLA

| 项 | 设计 |
|---|---|
| 适用范围 | 待办、工单、工作流步骤、预警认领等任意「有时限的对象」 |
| 计时 | 创建/认领/暂停/恢复事件驱动，支持节假日日历与工作时间段 |
| 节点 | 临期提醒（默认剩余 1/3 或 30 分钟）、最终提醒、逾期、逾期升级 |
| 升级链 | 责任人 → 上级 → 值班长，逐级可配，触发后写审计 |
| 暂停 | 等待外部响应时可暂停计时，需记录原因 |
| 统计 | 按期完成率、平均处理时长、逾期分布，供进化环回收 |

### 3.5 统一身份治理

| 项 | 设计 |
|---|---|
| 权限点注册 | 插件在清单中声明权限点，内核启动时合并进 `PERMISSION_DEFINITIONS`，与既有 48 权限点统一管理 |
| 命名规范 | `<plugin>:<resource>:<action>`，如 `sentiment:topic:edit` |
| 角色模板 | 内核提供基础角色，插件可声明「推荐角色」（如舆情分析师），安装时提示管理员一键创建 |
| 委派与代理 | 支持临时授权与离职交接，全程留痕 |
| 数据权限 | 行级隔离（租户/组织/所属人），由内核统一注入过滤条件，插件不得自行拼接 |
| 审计 | 登录、授权、越权拦截、敏感操作统一入审计日志 |

### 3.6 模型路由

| 项 | 设计 |
|---|---|
| 能力声明 | 业务只声明「做什么」（如 `emotion.classify` / `text.summarize`），不指定模型 |
| 路由策略 | 本地优先 → 本地不可用降级云端（默认关闭）→ 全不可用走规则兜底；按任务类型、数据敏感级、成本上限选择 |
| 数据分级 | 敏感数据强制本地，禁止出网（配置项白名单控制） |
| 计量 | 记录调用量、耗时、失败率、tokens，供成本与容量分析 |
| 缓存 | 相同输入指纹缓存结果，降低重复推理 |
| 降级开关 | 一键全局降级到规则引擎，运维可在故障时快速止损 |
| 硬件适配 | 复用既有 WMI + nvidia-smi 探测，按显存分档推荐可用模型（3060 12G → 7B–14B 量化） |

## 4. 插件清单规范（plugin.yaml）

```yaml
id: sentiment                 # 唯一标识，小写，禁止与内核/其它插件重复
name: 舆情监测
version: 1.0.0
kind: official                # official | community
min_kernel_version: 0.11.0
author: BY LAOMENG 网络工作室
description: 全网舆情采集、情感打标、热点聚类与预警
entry: backend.main:register  # 内核加载入口

namespace:                    # 隔离与命名
  tables: os_sentiment_       # 表前缀，必须独占
  events: sentiment.          # 事件前缀
  permissions: sentiment:     # 权限前缀

permissions:                  # 权限点声明（注册进统一 RBAC）
  - code: sentiment:topic:view
    name: 查看舆情主题
  - code: sentiment:topic:edit
    name: 编辑舆情主题

roles:                        # 推荐角色模板
  - code: sentiment_analyst
    name: 舆情分析师
    permissions: [sentiment:topic:view, sentiment:topic:edit]

events:
  publish: [sentiment.emotion.labeled, sentiment.alert.created]
  subscribe: [core.data.collected]

models:                       # 声明的模型能力需求
  - capability: emotion.classify
    sensitive: true           # 敏感数据 → 强制本地

jobs:                         # 定时任务声明
  - id: collect
    schedule: "*/10 * * * *"
    handler: collect_task

ui:
  menus:
    - path: /sentiment
      title: 舆情监测
      icon: radar
```

**校验规则**：`id` 唯一、`namespace` 不重叠、`min_kernel_version` 满足、权限点不冲突、表前缀未占用、签名有效（official 包）。任一不过即拒绝安装并给出明确原因。

## 5. 插件 SDK（对外最小接口集）

插件作者仅依赖 `opscompass-sdk`，不接触内核内部实现。

| 分类 | 接口 | 说明 |
|---|---|---|
| 数据 | `db.session()` | 只能访问自身命名空间表 |
| 事件 | `bus.publish(name, payload)` / `bus.subscribe(name, handler)` | name 必须落在自身命名空间 |
| 权限 | `auth.require(perm_code)` / `auth.check(user, perm_code)` | 统一鉴权 |
| 配置 | `config.get/set(key)` | 独立配置分区 |
| 模型 | `model.run(capability, input, **opts)` | 走路由，不直连模型 |
| 日志 | `log.info/warn/error` | 自动带 trace_id 与 plugin_id |
| 定时 | `job.register(id, cron, handler)` | 由内核调度，不自行起进程 |
| 存储 | `storage.save/read(path)` | 插件私有空间，走统一文件服务 |
| 待办 | `task.create(title, sla=...)` | 自动挂 SLA 与升级链 |
| 前端 | `ui.register_menu/route` | 动态注入 |

**接口稳定性承诺**：SDK 主版本内向后兼容；弃用项提前一个次版本标注，下个大版本移除。

## 6. 与既有版本的兼容与迁移

| 项 | 策略 |
|---|---|
| 既有 15 接口模块 | 保持可用；逐步将内部调用改为发事件，不改对外接口 |
| 既有 54 表 | 不动表结构；内核新增表统一前缀 `os_core_` |
| 既有 48 权限点 | 保持编码不变，与插件权限点合并管理 |
| 既有 138 接口路径 | 不变，避免前端与外部集成返工 |
| 数据库迁移 | 新增迁移脚本，可回滚；上线前在副本库演练 |
| 回退方案 | 内核能力可通过配置开关逐个关闭；关闭后回到 v0.10.1 行为，不丢数据 |

**兼容红线**：v0.11.0 升级过程中，任何既有页面不得出现功能回归；升级与回退均在一次操作内完成，无需手工改库。

## 7. 安全边界

1. 插件安装包必须校验签名（official 包），校验失败拒绝安装；
2. 插件不得执行任意系统命令，不得访问内核私有目录与其它插件数据；
3. 敏感数据模型调用强制本地，出网行为需显式配置并留痕；
4. 插件越权访问一律拦截并记审计，连续多次越权可自动禁用插件；
5. 内核升级、插件安装/卸载属敏感操作，需二次确认并记录操作者。

## 8. 落地顺序与里程碑

| 阶段 | 交付 | 说明 |
|---|---|---|
| M1 事件总线 | `core/bus` + 迁移 + 单测 | 最先落地，后续能力依赖它 |
| M2 插件运行时 + SDK | `core/plugin` + `sdk` + 清单校验 | 与 M1 可并行，接口先冻结 |
| M3 统一身份治理 | 权限点注册 + 角色模板 + 数据权限注入 | 依赖 M2 清单解析 |
| M4 任务 SLA | `core/sla` + 待办接入 | 依赖 M1 |
| M5 工作流引擎 | `core/workflow` + 3 个内置模板 | 依赖 M1/M4 |
| M6 模型路由 | `core/model_router` + 降级开关 | 依赖 M2 能力声明 |
| M7 试点插件 | 用风险域第一份 PRD 做首个官方插件 | 验证全链路 |

**关键前置**：M2 的 `plugin.yaml` 与 SDK 接口一旦冻结，M3–M7 才可并行开工。

**落地顺序决策（D8 已决，2026-10-08）**：按 **M1 → M2** 顺序开工，不采用「先做 M7 试点反向验证」。

理由：
1. M1 是唯一被其余全部能力依赖的底座，推迟则 M4 任务 SLA、M5 工作流引擎均无法开工，总工期反而拉长；
2. M2 未落地时 M7 试点无处挂载，试点只能退化为「内核内置」，与插件化目标相悖；
3. 反向验证的诉求可由 M1/M2 自身验收覆盖（A2 隔离性、A3 事件可靠性），无需等到业务域才验证。

**M1 进展**：已完成——`app/core/bus/`（发布/派发/退避重试/死信/重放/租约回收/位点/积压统计）、`app/models/kernel.py`、迁移 `a1f2c3d4e5b6`、单测 `tests/test_event_bus.py` 9 项通过。

## 9. 验收标准

| 编号 | 验收项 | 通过条件 |
|---|---|---|
| A1 | 插件装卸 | 不重启内核，安装→启用→禁用→卸载全流程成功，且不影响其它插件 |
| A2 | 隔离性 | 插件无法访问非自身命名空间表与事件；越权被拦截并审计 |
| A3 | 事件可靠性 | 消费方崩溃后重启，事件不丢（至少一次）；死信可查可重放 |
| A4 | 工作流恢复 | 流程执行中强制重启，恢复后从中断步骤续跑，无重复副作用 |
| A5 | SLA 准确性 | 临期/逾期/升级触发时间误差 ≤ 1 分钟 |
| A6 | 模型降级 | 关闭本地模型后自动走规则兜底，业务不报错，恢复后自动回升 |
| A7 | 兼容性 | 既有 138 接口 / 13 页面零回归；升级与回退一次操作完成 |

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 事件表膨胀 | 库容与性能下降 | 7 天热 + 归档；订阅方及时消费；监控积压 |
| 插件质量不可控 | 影响内核稳定 | 官方插件走签名校验；社区插件默认禁用、需人工启用 |
| 接口过早冻结 | 后期改动成本高 | M2 前留 1 轮内部评审，冻结后仅允许向后兼容扩展 |
| 改造范围失控 | 延误工期 | 严守「不新增业务页面」，既有模块仅在必要时改为发事件 |
| 权限点膨胀 | 管理复杂 | 权限点按域归组，角色模板化，禁止为单点需求建角色 |
